# 06. 結果画面の「もう一度占う」を押すと /shuffle でなくトップに戻ることがある

- **日付/場所**: 2026-09-14（独立テスト設計で検出。実機報告は無し）/ `frontend/src/pages/ResultPage.tsx`
- **症状**: 「もう一度占う」（reset → `/shuffle`）を押したのに、jsdom のテストでは `/` に着地した。
  「トップへ戻る」も同型（reset → `/`）。エラー状態の「トップへ戻る」は reset を呼んでいなかった。
- **原因**: `status === 'idle'` なら毎描画で `<Navigate to="/" replace>` を返していた。reset() は zustand の
  同期通知で即座に idle の描画を起こすため、その Navigate と続く `navigate('/shuffle')` が競走する。
  仕様（v3 §5.4）の意図は「直接 URL 到達など結果が無いときはトップへ」であり、毎描画の判定は過剰だった。
- **対処**: idle の判定をマウント時点の 1 回にした（`useState(() => status === 'idle')`）。
  エラー状態の「トップへ戻る」にも reset を追加（§5.4「占い状態をリセットして / へ」）。
- **同時に直したもの**: カード詳細で存在しない id のとき英語の `Card not found` がそのまま出ていた →
  日本語の固定文言に。`?orientation=` が片面表示になっていた → 仕様どおり両面（指定側を先）に。
- **再発防止**: `tests/components/ResultPage.test.tsx`（reset 後に `/shuffle` へ着く・error の「トップへ戻る」で idle）、
  `CardDetailPage.test.tsx`（not found の文言・両面と順序）。`docs/検査と門.md` #18・#19
- **アプローチへの反映**: 中央 `approaches/仕様書駆動で挙動を変える.md` の既存の判断基準（本物同士の経路・独立設計）で拾えた例。
  新設なし。テスト環境側の学び（framer-motion の完了コールバック）は中央 `reports/124`
- **事前の質問**: 「直接到達時のリダイレクトを、毎描画で判定するかマウント時に判定するか」は設計時に決められる
  （→ 中央 approaches/画面と入力の設計で先に決めること.md の離脱経路の質問に近い。今回は既存行を指す）
