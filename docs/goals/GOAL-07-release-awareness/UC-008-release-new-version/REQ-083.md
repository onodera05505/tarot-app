# REQ-083

> 保持の仕組みを登録できたホーム画面またはブラウザのアプリが新しい版へ入れ替わっている最中でなく、占う人が占いの途中でもないとき、問い合わせで Web 配信元に新しい版があると分かったら、システムは占う人の操作なしに新しい版へ入れ替わる。

## 検証方針

- **分割クラス**:
  - `#registers-immediate` — 保持の仕組みを、契約の registerSW が求める即時の指定（immediate）で登録する
  - `#swap-outside-reading` — 占いの途中でない（トップを示し、占い状態が idle）ときに新しい版があると分かる（契約の onNeedRefresh）と、確認を求める表示を出さずにその場で入れ替える（契約の updateSW）
- **尽きている根拠**: 前提は「保持の仕組みを登録できた」かつ「入れ替わっている最中でない」かつ「占いの途中でない」。観測点は、入れ替えの入口を持つ登録（契約の registerSW の必須の指定）と、新しい版があると分かった時点で操作を挟まず入れ替えること（確認の表示が無く、契約の updateSW が呼ばれる）の 2 つで、片方だけが壊れうる。占いの途中（UC-008 の表の前書きの 3 つの状態）に分かった場合は REQ-128 が持つ。
- **境界の扱い**: 占い状態が error の占い結果を示している間は、表の前書きの定義（儀式の中・drawing・drawn の占い結果）に入らないので文の上ではこの要件の側だが、意図の確認が要るためクラスにしない（下の検証しない）。
- **検証しない**: 実際に新しい版へ入れ替わること（待機中の版の有効化と開き直し）は、本物のブラウザの保持の仕組みでしか起きないため。占い状態が error の占い結果を示している間、および占い状態が drawn のまま占い結果以外の画面を示している間に分かった場合（文の上では途中でないが、意図が未確認で、後者へ移る操作が用語集に無い）。新しい版へ入れ替わっている最中に分かった場合と、保持の仕組みを登録できていないブラウザは、要件の条件の外で UC-008 の状態表でも `?` のため。
- **参照先**: `frontend/tests/UC-008-swap-timing.test.ts::新しい版があると分かったときの入れ替えの時機（UC-008）` の「占いの途中でないとき」
