# REQ-001

> 通常占いで結果の確定が起きたとき、システムは、端末に記録できるかぎり、その占い結果（カード・正逆・キーワード）とその日時を、占う人の操作なしに、カテゴリ名を添えずに占い履歴の先頭へ加えて端末に記録する。

## 検証方針

- **分割クラス**:
  - `#prepend-to-existing` — 既に記録がある占い履歴へ加えると、新しい占い結果が先頭に来て既存の項目はその後ろに順に残る
  - `#entry-content` — 加えた項目にカード・正逆・キーワードと、記録したときの日時がそろって記録される
  - `#recorded-on-confirm` — 結果の確定だけで、占う人の操作なしに占い履歴に 1 件加わる
  - `#no-category-label` — 儀式へ持ち込んだカテゴリと回答が無い占い（通常占いと、詳しく占うの質問の途中で儀式へ移り、持ち込んだカテゴリと回答が無いままの占い）の結果の確定では、カテゴリ名を添えずに記録される
  - `#not-recorded-on-failure` — ストップで抽選に失敗して結果の確定が起きなければ、占い履歴には何も加わらない
- **尽きている根拠**: 入力は「ストップの時点の抽選の成否（成功したときだけ結果の確定になる）」「確定した占い結果」「確定前の占い履歴（空／記録あり）」の組。空への追加は先頭＝唯一の項目になるので #prepend-to-existing に含まれる。上限件数に達している場合は REQ-002、記録内容が読めない場合は REQ-003 に分けてある。「端末に記録できるかぎり」の外（端末へ書けない）は REQ-004 に分けてある。記録の中身（#entry-content）・カテゴリ名を添えないこと（#no-category-label）・記録の起こり方（#recorded-on-confirm）は互いに独立に壊れうるので別クラスにする。儀式へ持ち込んだカテゴリとすべての回答が残っている占い（前の回に持ち込んだ分が残っている場合を含む）は、UC-001 の表の列の分け方に従って REQ-005 に分けてある
- **境界の扱い**: `#not-recorded-on-failure` は引き金（結果の確定）のすぐ外側。BR-004 が「結果の確定ごとの占い結果だけ」を記録するとし、用語集が抽選の失敗を結果の確定でないとするので、この要件のクラスとする。抽選に失敗したストップでカードも正逆も決まらず占い状態が error になることは REQ-057（UC-006 の要件）の `#not-fixed-on-failure` が持ち、占い履歴は見ない
- **検証しない**: 複数のタブで同時に結果が確定したときの取りこぼし（UC-001 の表の ? 列。望む振る舞いが未決のため）。項目の `id`（契約は文字列であることだけを定め、要件はその形も一意性も求めていないため）。記録されるカードの英名・種別・解説文・アルカナ番号・画像の場所（要件が求めるのはカード・正逆・キーワード・日時で、どのカードかは識別番号と和名で見分ける）。カテゴリ名として空の文字列を渡した場合（契約 `addToHistory` の性質で、要件の文の入力ではないため）。ストップのあとに儀式の途中で離れた場合の記録（REQ-114、UC-006 の要件が持つ）
