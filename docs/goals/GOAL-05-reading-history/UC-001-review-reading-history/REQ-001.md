# REQ-001

> 通常占いで結果の確定が起きたとき、システムは、端末に記録できるかぎり、その占い結果（カード・正逆・キーワード）とその日時を、占う人の操作なしに、カテゴリ名を添えずに占い履歴の先頭へ加えて端末に記録する。

## 検証方針

- **分割クラス**:
  - `#prepend-to-existing` — 既に記録がある占い履歴へ加えると、新しい占い結果が先頭に来て既存の項目はその後ろに順に残る
  - `#entry-content` — 加えた項目にカード・正逆・キーワードと、記録したときの日時がそろって記録される
  - `#recorded-on-confirm` — 結果の確定だけで、占う人の操作なしに占い履歴に 1 件加わる
  - `#no-category-label` — カテゴリ名を添えずに記録される（通常占い。詳しく占うの質問の途中で儀式へ移った占いも、UC-001 の表でこの要件に当たる）
- **尽きている根拠**: 入力は「確定した占い結果」と「確定前の占い履歴（空／記録あり）」の組。空への追加は先頭＝唯一の項目になるので #prepend-to-existing に含まれる。上限件数に達している場合は REQ-002、記録内容が読めない場合は REQ-003 に分けてある。「端末に記録できるかぎり」の外（端末へ書けない）は REQ-004 に分けてある。記録の中身（#entry-content）・カテゴリ名を添えないこと（#no-category-label）・記録の起こり方（#recorded-on-confirm）は互いに独立に壊れうるので別クラスにする
- **検証しない**: 複数のタブで同時に結果が確定したときの取りこぼし（UC-001 の表の ? 列。望む振る舞いが未決のため）。項目の `id`（契約は文字列であることだけを定め、要件はその形も一意性も求めていないため）。記録されるカードの英名・種別・解説文・アルカナ番号・画像の場所（要件が求めるのはカード・正逆・キーワード・日時で、どのカードかは識別番号と和名で見分ける）。カテゴリ名として空の文字列を渡した場合（契約 `addToHistory` の性質で、要件の文の入力ではないため）
- **参照先**: `frontend/tests/history.test.ts::占い履歴（仕様書 v3 §4.3）`、`frontend/tests/UC-001-history-record.test.ts::占い履歴への記録: 項目の中身（UC-001）`。#recorded-on-confirm は儀式のストップを通すテスト（UC-006 の `frontend/tests/components/ShufflePage.test.tsx` など）が持つ
