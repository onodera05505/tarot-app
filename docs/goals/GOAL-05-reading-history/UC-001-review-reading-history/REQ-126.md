# REQ-126

> 占う人が全削除を選んで確認に承諾しても占い履歴を端末から消せなかった場合、システムは消せなかったことを示し、端末の占い履歴も示している一覧も変えない。

## 検証方針

- **分割クラス**:
  - `#operation-raises-on-remove-failure` — 契約 `clearHistory` は、端末から消せないとき失敗を外に出し（`errors[0]` STORAGE_WRITE_FAILED、例 `removeRejected`）、端末の占い履歴を残す
  - `#shows-failure` — 承諾の後に端末から消せなかったとき、消せなかったことが示され、履歴がないことの表示にはならない
  - `#keeps-device-and-view` — 承諾の後に端末から消せなかったとき、端末の占い履歴も示している一覧も承諾の前のまま（全削除の操作も残る）
- **尽きている根拠**: 失敗の経路は契約 `clearHistory` の `errors` の 1 つ（STORAGE_WRITE_FAILED）だけで、隣接する失敗が無いので優先順位のクラスは要らない。観測は「操作が失敗を外に出す」「消せなかったことを示す」「何も変えない」の 3 つで、それぞれ片方だけが壊れうる（消せなかったことを示しつつ一覧を空にする、一覧を保ちつつ黙る）ので分ける。記録の件数（上限件数未満・上限件数）で振る舞いは変わらない
- **境界の扱い**: 該当なし（端末が消去を受け付けるか否かの 2 値）
- **検証しない**: 端末から消せたとき（REQ-011）。確認を取り消したとき（REQ-012）。空・読めないときの承諾（全削除の操作を出さないので起きない）。消せなかったことを示す文言そのもの（用語集に語が無く、文で一意に決まらない。テストは「削除」の語を含む新しい表示が出ることだけを見る）。実ブラウザで端末が消去を拒む実際の条件（容量・プライベートモードなど。jsdom では該当メソッドの差し替えで起こす）
