## 4. Phase D: /deep → /shuffle 遷移の引っかかりを実測（調査のみ、コード変更なし）

**意図:** 8/22 から持ち越しの「数秒引っかかる」件。共通ルール 3-3
（測ってから言う）に従い、原因の断定より先に再現と計測を行う。

**仮説:** 裏面画像 `000.webp` が 1024×1536・582KB で、儀式画面はこれを 22 枚の
`<img>`（表示は 72×108 CSS px、DPR 3 で 216×324）として 3D レイヤー化する。
デコードと GPU テクスチャの負荷が原因ではないか。

**計測方法:** 本番ビルドを `vite preview` で配信し、インストール済み Chrome を
puppeteer-core で自動操作。iPhone 相当（390×844・DPR 3・タッチ）+ CPU 6 倍減速。
GPU は Apple M4 の Metal が使われていることを WebGL の renderer で確認。
/deep でカテゴリ → 3 問回答 → intent 画面 → 「シャッフルへ」→ 22 枚描画までを
実走し、rAF のフレーム間隔と Long Task を記録。裏面画像を 216×324 に縮小した
版とも比較（リクエスト差し替え）。各 3〜4 回。スクリプトはスクラッチパッドの
`measure.cjs`（リポジトリ外）。

**結果:** **再現せず。** 3 問目回答 → intent 画面の表示まで 350〜440ms
（うち 250ms はページ遷移のクロスフェード）、「シャッフルへ」→ 22 枚描画まで
60〜76ms。その後 3 秒間のフレーム落ち（50ms 超）は 0、Long Task 0。
画像の縮小版でも差なし。初回起動の 1 回だけ 167〜200ms のコマ落ちが出た
（ブラウザ起動直後のウォームアップ）。

**判断:** 画像サイズ仮説は**このデスクトップ環境では棄却**。ただし実機
（iOS Safari / Android Chrome）の GPU・メモリ条件は再現できていないため、
実機由来の可能性は残る。もう一つの可能性は**意図的な演出の待ち時間**:
intent 画面はテキストが 0.15s 遅延 + 0.7s フェード、ボタンが 0.7s 遅延 +
0.5s フェードで、回答タップから「シャッフルへ」が押せるまで約 1.5s。
これを「引っかかり」と感じている可能性がある。

**次の一手（ユーザーに確認）:** 引っかかりの位置が ①回答タップ → 「占うことを
思い浮かべて」が出るまで、②「シャッフルへ」タップ → カードが動き出すまで、の
どちらか。端末と OS も併せて。①なら演出時間の調整（仕様 §5.3 の文面変更）、
②なら実機で `000.webp` 縮小版の A/B を試す。

**副産物（事実として記録、対処は保留）:** 裏面画像は表示サイズの約 4.7 倍の
解像度で配信されている（582KB → 縮小なら数十 KB）。表面 22 枚も 440〜680KB。
初回ロードと端末メモリの観点では縮小の余地があるが、引っかかりの原因とは
確認できていないため今回は触らない。

**主な変更ファイル:** `history/2026-09-02.md`（本記録のみ）
